# brainstorming

复杂实现前的澄清方法。目标不是写设计文档，而是把「模糊的诉求」变成「可验收的指令」，
避免在错误方向上消耗工具调用预算。

## 何时触发

- 任务描述缺少可验证的完成标准（「优化一下性能」「完善错误处理」）
- 存在多种实现路径且成本差异大（改配置 vs 改架构）
- 任务提到「支持/兼容/迁移」但没有说清范围边界
- 动手前你发现自己说不清「改完后怎么证明改对了」

以上一条都不命中时，**不要**用本技能——直接按任务指令推进。

## 执行步骤

1. **先自己找答案再问**：任务里的模糊点，先用 read_file / grep 查代码，
   大部分「用什么框架、请求怎么封装」类问题代码里已有答案；
2. **剩余疑问按影响排序**：只问影响方案选择的疑问（做哪个方向），
   不问实现细节（怎么写）；单次提问合并成一组，减少往返；
3. **对齐后写出验收标准**：把目标改写成 3~5 条可验证的断言
   （「跑 X 命令输出 Y」「改后 Z 行为不回归」），作为推进与收尾的依据；
4. **计划分层**：把实现拆成可独立验证的小步，每步对应一个工具调用预算，
   先做最能证伪方向的那一步。

## 工程约束

- 澄清问题直接输出给用户（当前轮无工具调用），不要自问自答；
- 查证类工具调用（read_file/grep）不消耗澄清轮次，优先使用；
- 验收标准必须来自真实工具输出可证明的行为，不要写「代码质量良好」类主观条款。

## 验收标准

- 任务产出前，你能在交付摘要里逐条对应验收标准给出「通过/未通过/未确认」；
- 每条「通过」都有工具输出背书；「未确认」如实标注。
