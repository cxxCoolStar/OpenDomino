# code-review

交付前的自查方法。目标不是替代人工评审，而是在改动交给用户之前，
用 git_diff 与 read_file 把「范围失控」「顺手多改」「改了没改对」三类问题拦在提交前。
自查的核心是范围纪律：交付物的边界必须与任务目标一致，多做的与漏做的同样是问题。

## 何时触发

- modify 类任务的主要改动已完成，进入收尾（即将给出交付摘要或执行 commit）
- 一次改动跨越多个文件，需要确认没有无关文件被带进来
- 修复过程中出现过返工、试错或中途换方案，需要确认最终留下的都是有效改动
- 交付前你说不清「这次到底改了哪些文件、每一处为什么改」

以下情况**不要**用本技能：

- 只读类任务（回答问题、检索、调研）没有交付物，无改动可查；
- 任务刚开工、改动尚未成形——此时应做的是规划而非自查；
- 用户明确要求跳过自查直接交付。

## 执行步骤

1. **先用 git_diff 看全部改动**：git_diff 给出工作区相对基线的完整差异，
   逐文件过一遍，在心里列出「文件 → 该文件改了什么 → 为什么属于本任务」的对应清单；
2. **核对范围纪律**：清单里出现「与任务目标无关、说不出为什么改」的文件或 hunk，
   即为混入改动——确认后用工具回滚该处，不要抱着「反正也要改」把它留在交付里；
3. **用 read_file 复读关键修改点**：diff 只显示局部，读改动所在函数/模块的完整上下文，
   确认新代码与周边风格一致、没有引用不存在的符号、没有残留调试输出与注释掉的旧代码；
4. **用 grep 查漏网引用**：改名、删函数、改签名时，grep 旧名称确认没有调用点漏改；
5. **跑可验证的检查**：改动涉及测试或脚本时，用 run_command 执行对应测试/编译，
   交付摘要里的「已验证」必须有命令输出背书；验证失败先修再交付，不带病提交；
6. **汇总自查结论**：按下方验收标准逐条自评，未通过的先修再交付；
7. **自查不过夜**：整个自查流程应在交付前一轮内完成，发现的问题当轮修复并复检，
   不把「已知有毛病」的改动交给用户。

## 工程约束

- 自查只用只读手段（git_diff/read_file/grep）加必要的验证命令，不在自查阶段顺手引入新改动；
- 发现问题的修复属于原任务范围；修复后必须重新走一遍本流程（diff 已变，结论要重下）；
- 新增文件与整文件重写同样进 diff 清单，接受范围核对，不因为「是新的」就免检；
- 自查发现方向性设计问题时，停下来向用户报告再动，不要在交付前自行大改；
- 环境脏数据（未跟踪的临时文件、本地产物）不算任务改动，确认与任务无关后保持原样，
  不要为「让 diff 干净」顺手删除不属于自己职责的文件。

## 验收标准

- 交付摘要能列出改动文件清单，每个文件对应一句「改了什么、为什么属于本任务」；
- diff 中不存在无法解释的 hunk；已回滚的混入改动在摘要中如实说明；
- 关键修改点经过 read_file 复读，无残留调试输出、无引用不存在的符号、无注释掉的旧代码；
- 涉及可执行验证（测试/编译）的改动，摘要中有对应的命令与结果，未验证的如实标注「未验证」。
