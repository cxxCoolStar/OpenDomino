# ADR-011 知识库文档自动同步：周期扫描 + Source 抽象 + 镜像删除

> 状态：已确认（2026-09-29 讨论定稿并实施）
> 日期：2026-09-29
> 前置依赖：ADR-002 三层记忆（L3 知识库、哈希幂等导入）
> 关联：ADR-009 旁听结论蒸馏（后台扫描器的装配模式）

## 背景

L3 知识库唯一的更新入口是手动 CLI `python -m app.docs.import_docs ../docs`
（见 ADR-002 §L3：正式知识库）。文档更新后没有任何自动机制触发重导入，
ConsoleAgent 检索到的一直是上次手动导入时的内容，直到有人记得跑命令。

一个决定方案形态的既有事实：导入是内容哈希幂等的——文件内容未变直接跳过，
变了才重切块、重 embedding（`backend/app/docs/knowledge.py` 的
`import_document`）。因此「全量重扫」的成本只是读文件加 sha256，同步机制
不需要精确感知哪个文件变化，轮询全量对比即可。

## 核心决议

触发机制选**周期扫描**（后台循环 + 启动同步），不选文件系统监听（watchdog）
或飞书手动指令，决定性因素是飞书云文档的接入预期：

1. 文件监听天然覆盖不了飞书文档——云端文档不存在本地文件事件，选监听意味着
   以后为飞书单独再造一套触发逻辑，维护两套同步机制。
2. 周期轮询对两种来源是同一模型：「定期问一遍有哪些文档、内容是什么 → 哈希
   对比 → 幂等导入」。本地目录与云端 API 在轮询模型下无区别；飞书 API 的速率
   限制也本就排斥高频事件式拉取。
3. 哈希幂等导入已存在，飞书文档进来后复用同一套「内容未变即跳过」，零额外成本。

删除语义选**镜像删除**：本次扫描缺席的文档从知识库删除其块与向量，知识库与
源目录严格一致。理由：docs/ 在 git 管理下，删除不丢历史；知识库的价值在于
准确反映当前知识。将来若出现「文档下线但知识要保留」的需求，应作为显式的
「归档」功能单独设计，而不是靠删除同步的漏洞实现。

链路总览：主进程 lifespan 启动 KBSyncer 后台任务，启动后先跑一轮全量同步
（后台执行，不阻塞服务就绪），之后每 `kbsync_interval_seconds` 全量扫一遍。
每轮同步向 SyncSource 要文档清单与内容，逐篇哈希幂等导入；本次缺席的
已有文档按镜像语义删除。更新延迟上限为一个扫描周期（默认 300 秒）。

### 架构决议：SyncSource 抽象

同步循环只面向 `SyncSource` 接口工作，不感知文档来自磁盘还是云端 API：

| 接口方法 | 职责 |
|---|---|
| `name` | 来源标识，作为 doc_id 前缀（本地源前缀为空） |
| `list_docs()` | 返回本轮可见文档列表 `[(doc_id, title)]` |
| `fetch(doc_id)` | 返回文档全文文本 |

第一期只实现 `LocalDocsSource`（扫 docs 目录 `*.md`），飞书源
（`FeishuDocsSource`，云文档转 Markdown）只留接口不实现。doc_id 用来源前缀
区分命名空间（本地 `decisions/xxx.md`，飞书 `feishu/<doc_token>`），两来源
不冲突。以后接入飞书文档是「新增一个类」，不是「改造同步架构」。

配套重构：现有 `import_document(path)` 从磁盘读文件，飞书文档内容来自 API
不走磁盘。因此把知识库导入拆出 `import_text(doc_id, title, text)` 作为
核心入口（哈希对比、切块、FTS、向量全部在里面），文件版
`import_document(path)` 变为读文件后调 `import_text` 的薄壳，CLI 行为不变。

### 运行决议：lifespan 装配与配置项

KBSyncer 挂在 main.py lifespan 做后台任务，装配模式与 ADR-009 蒸馏扫描器
一致（asyncio 循环 + stop 信号）。两个差异：蒸馏扫描器按固定间隔 sleep，
KBSyncer 启动后立即先跑一轮再进入间隔等待（重启即收敛一次）；同步单轮
异常捕获记日志后继续下一轮，不影响主链路。

新增配置项（默认值对应本 ADR 配置契约）：

| 配置项 | 默认 | 说明 |
|---|---|---|
| `kbsync_enabled` | `true` | 总开关；false 不启动同步循环 |
| `kbsync_interval_seconds` | `300` | 扫描间隔；docs 为 git 管理的低频内容，5 分钟延迟足够 |

doc_id 沿用现有规则（相对 docs 根的 POSIX 相对路径），同步器与既有 CLI 导入
的数据无缝兼容，不重复建条目。

### 删除决议：镜像语义与向量清理

每轮同步开始时收集本轮 doc_id 集合；导入完成后，对知识库中存在而本轮缺席的
doc_id 执行删除：删 `docs` 行、`doc_chunks` 行、FTS 行与 Chroma 向量。
单篇文档删除整体成功或整体失败，失败记日志不中断其余文档的清理。

首次部署等价于全量导入；服务重启不需要特殊处理——下一轮扫描的哈希对比
天然幂等收敛。知识库为空库时启动同步即完成首轮建库，无需手动跑 CLI。

## 后果

正向：文档更新后最多一个扫描周期（默认 5 分钟）自动进入知识库；重启后
自愈（含向量缺失补齐）；新增飞书文档源只需实现一个类。

代价：知识库删除不再有「误删保护」（镜像语义下源目录删文件即知识库删除），
由 git 历史兜底；每轮全量扫描在文档量大时有 IO 放大，当前 docs/ 规模
（十几篇）可忽略，文档量上千后需引入 mtime 预筛（本 ADR 不做）。

排除项：不做飞书手动指令触发（要即时生效可把间隔调小，无需指令入口）；
不做文件监听（理由见核心决议）；不做删除前的确认流（同步是基础设施而非
对话行为，镜像语义即契约）。
