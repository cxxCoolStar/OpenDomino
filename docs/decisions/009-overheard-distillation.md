# ADR-009 旁听结论蒸馏：群聊讨论经确认沉淀为团队记忆

> 状态：已确认（2026-09-28 讨论定稿并实施）
> 日期：2026-09-28
> 前置依赖：ADR-002 三层记忆（KBase 确认流）、ADR-008 飞书通道（旁听缓冲）
> 关联：ADR-003 ConsoleAgent（Session 状态机）

## 背景

ADR-008 的旁听链路已将群内非 @ 消息全量接收：窗口内合并进上下文段 2，窗口外落 L2
observed_messages（存而不检索）。但「看到」不等于「记住」——KBase 现有三条提炼触发
（任务完成、用户纠正、显式 `/沉淀`）都要求有人 @ 机器人转述。群友自然讨论中拍板的结论，
只要没人转述，滑出旁听窗口后就永久沉在原始消息堆里，永远不会成为记忆。

本 ADR 在 ADR-002「提炼触发时机」预留的「明确结论信号触发」路线上落地第四条入口：
**旁听结论蒸馏**——群空闲时对新增旁听消息做一次 LLM 蒸馏，产出候选结论走确认流，
经人确认后写入 KBase。

核心不变量（沿 ADR-002）：**自动的是检测，不自动的是写入**。蒸馏永远不直接写团队
记忆，提议必须经群内确认词确认；原始旁听消息永远不进 KBase，KBase 只收脱离原对话
可读的声明式条目。

## 核心决议

ADR-009 做出四组决议：触发机制（后台空闲扫描）、水位线治理（游标落库与三态语义）、
蒸馏调用（输入产出与确认流衔接）、过时内容处理（supersedes 最小实现）。

链路总览：后台扫描器发现群空闲后，对「水位线之后」的旁听缓冲消息做一次蒸馏 LLM
调用，产出候选结论草稿写入 `pending_memory` 槽位；群内确认后条目落 KBase，
水位线推进；取消同样推进（不再重提）；过期不推进（下个空闲周期重蒸重提）。
新结论与旧条目冲突时产出带 `supersedes_id` 的替换草稿，确认后旧条目转 archived。

四组决议共同服从一条既有红线（见 ADR-002 §总体决议）：**自动的是检测，不自动的是
写入**。蒸馏永远不直接写团队记忆，提议必须经群内确认词确认；原始旁听消息永远不进
KBase，KBase 只收脱离原对话可读的声明式条目。

### 触发决议：后台空闲扫描

触发采用常驻后台扫描器，不采用惰性触发。扫描器每 `distill_scan_interval_seconds`
（默认 60 秒）扫一遍各群，距上一条旁听消息超过 `distill_idle_minutes`（默认 10 分钟）
且冷却已过，即对该群触发蒸馏。

- 选空闲触发而非惰性触发的决定性理由：确认提议的时效性。惰性触发的检查点在
  下一条消息到达时，蒸馏恰好在有人开口时执行（占群锁、滞后回答），提议总是
  在讨论恢复后才出现，确认质量打折；扫描器让蒸馏跑在静默期，提议在讨论结束后
  约 10 分钟出现，趁热确认。
- 活跃兜底：未蒸馏消息攒到 `distill_force_threshold`（默认 50 条）强制触发一次，
  防止永不停歇的群永远等不到空闲。强行触发可能蒸出半截结论，由确认门事后兜底。
- 空闲判定用本地接收时间（`received_at`），不用飞书消息时间戳，避免两端时钟偏差。
- 两级冷却门（对所有触发统一生效）：距上次成功蒸馏不足
  `distill_cooldown_minutes`（默认 360 分钟，即每群每天最多 4 次）跳过；距上次
  失败蒸馏不足 `distill_failure_retry_minutes`（默认 30 分钟）跳过。

### 水位线决议：游标落库与三态语义

水位线（watermark）是 per-chat 游标，记录该群旁听消息已蒸馏到哪一条，持久化在
SQLite `distill_state` 表（重启后恢复，不重蒸不漏蒸）。蒸馏范围恒为「时间戳不早于
水位线」的旁听消息，单次最多 `distill_batch_max`（默认 200 条，最老优先），
积压借后续空闲周期逐批推进。

#### 水位线的比较维度与首见初始化

水位线与「已蒸馏范围」的判定统一按**消息时间戳**（飞书服务器钟）比较：蒸馏范围
查询、prune 的「已蒸才可清」条件、水位线推进目标三者同维度，保证「不在任何未蒸馏
集合里的消息才可清」。跨端时钟偏差的最坏影响是边界消息偶尔重复进入下一批
（LLM 再看一次，无正确性影响）；本地接收时间 `received_at` 不用于水位线判定——
回拉旧消息的 received_at 恒为落库时刻，按它判「已蒸」会让回拉存量永远清不掉。

首见初始化：某群第一次被扫描器看到时，水位线置为当时表内最新本地接收时间——
首次部署不蒸 7 天回拉的存量讨论（老结论确认时效已过，且首日会爆发式产生提议；
存量消息的消息时间戳恒早于落库时刻，天然落在首见锚点之前）。部署后水位线随三态
语义演进并持久化，重启期间漏收的消息（时间戳晚于水位线）重启后仍会被正常蒸馏。

#### 三态推进语义

水位线只在人表态时推进，三态语义如下：

| 群友反应 | 结果 | 水位线 |
|---|---|---|
| 确认 | 条目入库 | 推进到本批最末时间戳 |
| 取消 | 不入库 | 推进到本批最末时间戳（人已明确拒绝，下周期不再重提） |
| 过期（60 分钟无人理） | 不入库 | 不动（下个空闲周期重蒸重提） |

过期不推进的理由：深夜发出的提议可能根本没人看见，若过期即推进等于系统擅自
判死该结论。重蒸代价是每冷却周期一次廉价 LLM 调用，第一版接受；「过期 N 次自动
放弃」计数器不做。无人理会的提议会让水位线停滞、每个冷却周期重复蒸馏一次，
属已知局限。

蒸馏 LLM 成功返回但判定「无可沉淀」时，没有提议对象，水位线直接推进（否则同一
范围每冷却周期空转一次）；失败（异常/解析失败）不推进。

### 蒸馏调用决议：输入、产出与确认流衔接

蒸馏由独立的 LLM 调用完成，模型用 `console_summary_model`（空则回落
`console_model`），超时沿 `console_llm_timeout_seconds`。输入为范围内旁听原文
+ 现有 KBase 条目（≤`kbase_full_load_threshold` 时全量注入，否则按讨论内容
召回，见 ADR-002 §KBase 检索），输出为结构化结论草稿 JSON 或「无可沉淀」
（不强行生成，沿 ADR-002 原则）。

蒸馏与确认流的衔接规则：

- 产出走 Session 的 `pending_memory` 槽位（payload 携带 `source=overheard` 与
  `watermark_ts` 目标值），确认词/取消词/@ 门控/TTL 沿 ADR-002 确认流现状；
  水位线推进动作由确认流拦截器在确认/取消时执行（单调取 max）。
- 提议消息标注来源为「群聊旁听蒸馏」，与人工 `/沉淀` 区分。
- 每次蒸馏最多产出 1 条提议（确认流单槽位；多候选取最重要一条，其余放弃）。
- 蒸馏的 LLM 调用不持群锁；LLM 返回后先做**写前校验**——若本群最后一条旁听消息
  的本地接收时间已变（讨论恢复），本轮作废：丢弃结果、不动水位线，下周期重蒸；
  校验通过后再拿同群 `asyncio.Lock` 写 Session（与消息管线互斥）。
- 槽位被人工提议（`/沉淀`、记住、纠正）占用且未过期时，蒸馏跳过、水位线不动；
  占用者已过期则惰性清理后照常写入（与确认流拦截器的惰性清理同规则）。
- 蒸馏 LLM 失败（429/超时/解析失败）：不推水位线，记失败时间进失败冷却。

### 过时内容决议：supersedes 最小实现

蒸馏时将新结论与现有 KBase 条目比对，判定为「冲突/替代」时产出替换草稿
（含 `supersedes_id` 指向旧条目），照常走确认流。确认后新条目 confirmed、
旧条目转 archived（不物理删除，留审计）；取消则新草稿删除、旧条目不动。
`supersedes_id` 指向的旧条目不存在或已非 confirmed 时，丢弃替代关系按普通
新条目处理。

召回过滤零改动：现有 recall 只取 confirmed，archived 自动退出上下文。

## 上下文与数据流（修订后）

旁听消息的生命周期新增「蒸馏」环节，全链路如下：

```text
飞书全量消息 → 旁听缓冲（observed_messages，含 received_at 本地接收时间）
    ├─ 窗口内：进上下文段 2（ADR-008 现状，不变）
    ├─ 水位线之后 + 群空闲/兜底：蒸馏调用 → 候选结论
    │       └─ pending_memory 提议 → 确认/取消/过期
    │               ├─ 确认 → KBase confirmed（supersedes 时旧条目 archived）
    │               ├─ 取消 → 水位线推进，不入库
    │               └─ 过期 → 水位线不动，下周期重蒸
    └─ 保留期清理：消息龄超限 且 消息时间戳在水位线之前 才可删
```

数据新增：

- `distill_state` 表：`chat_id` 主键、`watermark_ts`（水位线，按消息时间戳比较）、
  `last_success_at` / `last_failure_at`（冷却锚点）；
- `observed_messages` 表增加 `received_at` 列（本地接收时间，空闲判定与写前校验用，
  不参与水位线判定）；
- `kbase_memories` 表增加 `supersedes_id`、`source_type`（manual / overheard /
  correction）、`source_chat_id` 列（溯源与来源标记）。

## 被拒档案与提议前查重闸（2026-09-30 增补）

背景：ADR-009 三态语义中「取消」的记忆是**位置性**的（水位线推过该段消息），
被拒结论本身不留任何痕迹。同一结论换措辞重提（或蒸馏范围覆盖到它时）会反复
打扰群里——运行第一天即出现同一结论被连提 4 次、人工连点 4 次取消的实际事故。
本增补为「明确拒绝过的结论」建立语义记忆，并在提议前做确定性查重。

### 被拒档案（rejected 状态）

- 复用 `kbase_memories` 表：取消时 overheard 来源的草稿不物理删除，改为置
  `status=rejected` 并记 `rejected_at`（新列，轻量迁移）；
- rejected 条目对召回/全量注入完全不可见（只取 confirmed），唯一用途是查重闸；
- **只留档 overheard 来源**：人工来源（`/沉淀`、记住、纠正）的取消是用户撤回
  自己的话，照旧物理删除；过期未理的提议也不留档（ADR-009 过期语义不变）；
- **半衰期 90 天**（`DISTILL_REJECTED_HALF_LIFE_DAYS`）：超期档案不再参与拦截，
  人的反对可随时间失效，提供翻案通道；数据不删。

### 查重闸（提议前确定性比对）

位置在 `_propose` 建草稿之前，纯代码机制（依据「能用代码机制解决的绝不加
prompt 规则」元原则——LLM 比较 429/超时/误判且昂贵，embedding 余弦比较
毫秒级、确定性、且「措辞变语义不变」恰是向量主场）：

1. 候选 statement 经 embedding 得向量（一次 API 调用）；
2. 与全体 confirmed 比对，余弦相似度 ≥ **0.85** → 重复，丢弃
   （收紧：此闸前面已有提示词软防线与人审兜底，误杀新结论不可逆）；
3. 与**本群**半衰期内 rejected 比对，≥ **0.80** → 被拒过，丢弃
   （放宽：唯一硬防线，误杀有 `/沉淀` 直达通道与半衰期翻案兜底；拒绝是本群
   人的表态，别的群拒绝不拦本群）；
4. 命中 → 静默丢弃、水位线照常推进（等同「无可沉淀」），**不发群消息**；
5. **fail-open**：embedding 未配置或调用失败时查重放行，降级回提示词软约束 +
   人审兜底，绝不阻塞蒸馏。

阈值不对称的原因：confirmed 侧误杀无补救（漏放重复最多少点一次取消），
rejected 侧误杀有翻案通道（漏放垃圾则直接打扰群里）。

  `source_chat_id`、`rejected_at`；

### 已知局限（本增补）

- 语义相近但结论相反的新约定（如推翻旧约定的新规范）可能被 confirmed 高相似
  误杀——现由人审确认流的 `/沉淀` 直达通道兜底；若误杀频发，再评估
  「向量粗筛 + LLM 精判」分层方案；
- 查重仅覆盖蒸馏提议路径，`/沉淀` 等人工入口不做查重（用户显式指令即表态）。

## 第一版明确不做（后续项）

以下项在讨论中识别为合理优化，第一版不做，待真实使用反馈后评估：

- TTL 分来源放宽（蒸馏提议 12 小时）、自动提议同源顶替——三态语义的过期重试
  已覆盖其动机；
- 蒸馏顺带更新段 3 历史讨论摘要（一次调用双产出）；
- 每日提议上限；
- SKILL 分流落地（流程类内容第一版仍走 KBase 路径）;
- `/记忆` 人工管理命令与后台管理系统（数据库可见性、日志管理）——后者值得
  单独立 ADR；
- KBase 条目按群隔离作用域（现状为全局共享，条目带 `source_chat_id` 可溯源）。

## 已知局限

第一版蒸馏只覆盖旁听消息流：结论若依赖此前 @ 问答的细节，蒸馏上下文可能不完整，
提示词要求上下文不足时宁缺毋滥。无人理会的提议会导致水位线停滞、每个冷却周期
重复蒸馏一次（每群每天最多 4 次廉价调用），第一版接受此浪费。隐私防线为提示词内置
ADR-002 不存储清单 + 确认流人审兜底，无独立过滤组件。LLM 判「无可沉淀」即推进
水位线，误判会漏提结论，由确认流的 `/沉淀` 人工入口兜底。

## E2E 验收项

`cd backend && python scripts/e2e_distill.py`，产出
`scripts/e2e_distill_report.json`，全部用例通过为验收标准：

1. 首见初始化：回拉存量（时间戳早于首见水位线）不被蒸馏；
2. 空闲触发：超阈值空闲 + 有未蒸馏消息 → 蒸馏并提议；
3. 写前校验：蒸馏期间讨论恢复 → 结果作废、水位线不动；
4. 三态语义：确认推进、取消推进、过期不推进（草稿物理删除）；
5. supersedes：确认后旧条目 archived、新条目 confirmed、召回不再命中旧条目；
6. prune 协同：水位线之前的过期消息被清、水位线之后的保留；
7. 冷却：成功冷却与失败冷却均生效，冷却过期后恢复；
8. 槽位占用：人工提议未决时蒸馏跳过、水位线不动；
9. 单提议上限：LLM 返回多条时只保存第一条；
10. 「无可沉淀」：无提议且水位线推进。
